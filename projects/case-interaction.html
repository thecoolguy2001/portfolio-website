Case Study 03

Exploring New Forms of Interaction

Audio, voice, motion and biometrics as inputs — which of them genuinely made an interface easier to use, and which ones only added a layer to explain.

The question

Audio, voice, motion, biometrics and AR are all available as inputs now. Which of them actually made an interface easier to use, and which only added a layer that had to be explained?

The position

A novel input earns its place when it removes a step the user was already performing. When it adds a step — a calibration, an initialisation, a thing to learn first — it needs to be worth the toll, and most are not.

Where it stands

Drawn from shipped work in Visualizer, Reflex-o, Fibber, Moodbeat, Motion Lab and Roulette, plus two AR projects still in development.

The question

Novel input has a toll

Every input beyond a pointer and a keyboard carries a cost that is easy to leave out of the pitch. Voice needs a quiet room. Motion needs the device held a particular way. Biometrics need a baseline. AR needs light, space and a surface. Audio-reactive interfaces need audio to actually be playing.

None of that makes these inputs wrong. It means the honest test is not “is this impressive” but “does this remove a step the user was already doing, or add one they now have to learn?”

Across the work below, the inputs that held up did the first thing. The ones that caused the most support burden did the second — and one of them is in the project I use most.

Audio as input

When the content drives the interface

Visualizer’s whole premise is that audio drives the visuals in real time through FFT analysis. The more interesting application came later, in Game Mode: rather than generating a difficulty curve, the game reads beat hits, frequency peaks and dynamics from the track itself. The user picks the music; the music picks the difficulty.

That is the clearest case of an input earning its place in any of this work. The alternative design — a difficulty selector — is a question the user has to answer before they can start, using information they do not have yet. Reading it from the song removes the question entirely. There is nothing extra to learn, because choosing a track is something the user came to do anyway.

The supporting decisions follow the same logic. Ten games, one per effect, each mechanic growing out of what that effect was already doing visually. Game UI overlays the canvas instead of replacing it, so immersion survives the toggle. The HUD — three hearts, a score line, the effect label holding its usual corner — stays identical across every game, so nothing has to be relearned between titles.

Where it went wrong

The initialisation that had to be documented three times

Browsers will not start an audio context without a user gesture. In Visualizer that gesture is the spacebar, and the start screen asks for it. The problem is what it silently gates: recording.

If a user begins a recording without ever having pressed spacebar, the recording captures empty audio and fails quietly. No error, no obvious cause, just a dead file. That is a textbook usability failure — an invisible precondition with a delayed, silent consequence.

The fix ended up being three layers of explanation: the requirement is called out in the H controls overlay, repeated in the manual, and a warning now fires inline when a recording starts from an uninitialised context. Three places is not elegant. A design that needs to be documented three times is telling you something.

The honest read is that this is a platform constraint dressed up as a design decision. The spacebar press doubles as the audio init, which is tidy framing — but it is tidy framing applied after the fact to a requirement the user never asked for and cannot see. It is the one place in the project where the interface asks the user to absorb a technical detail, and it has cost more support surface than any feature.

What restraint looked like

Removing the step, not adding a panel

Draw Mode turns the active effect into a brush: click and drag spawns instances along the cursor path, and each stroke remembers which brush drew it, so switching effects mid-drawing layers cleanly. Every interface decision around it was about not building the panel the feature seemed to need.

One key, one undo

Backspace erases the last stroke. No multi-step history, no undo panel. Fast iteration mattered more than complete recoverability, and a history UI would have sat permanently on top of the canvas.

Controls stay on the keyboard

Arrow keys cycle brushes, number keys set stroke intensity. No on-screen brush picker, no eraser button. The chromeless rule that governs the player governs the creative tool too.

One word of state

A single low-contrast status line reads draw mode: on. No popovers, no panels. If the mode is obvious from what the canvas is doing, the UI only needs to confirm it.

Fade as a performance tool

Press F and strokes auto-fade over ten seconds, then free their memory. Built for live VJs who need the canvas to keep evolving without stopping to clean up — the constraint and the aesthetic turned out to be the same feature.

The other restraint case is codec selection. Recording picks VP9, VP8 or H.264 depending on the browser, and the container follows. The user never sees the choice, because it is not a choice they have any basis for making.

Motion and voice

Inputs that replace a step

Motion Lab treats the Flipper’s Video Game Module as an instrument rather than a controller: peak g-force, rotation rate, swing tempo, logged at 100 Hz to CSV. Motion here is not a gesture language to learn — it is the measurement itself. The device captures and hands off; analysis happens elsewhere. The input removes the step of instrumenting something manually.

Reflex-o uses voice commands on a watch, which works for a specific reason: the alternative is tapping a target on a 40mm screen while reacting quickly, which is a worse interaction, not a more familiar one. Voice is not decorating the game — it is the only input fast enough for the mechanic. The haptic response closes the loop in the same channel-appropriate way.

Roulette is the smallest example and the clearest about intent. Buzzer, screen, vibration and LED together make a six-chamber game feel theatrical on hardware mostly used for utilities. No single channel is doing much; the combination is the entire product.

Biometrics

The input with the longest setup cost

Fibber baselines heart rate, then watches live BPM shift during questioning, structured as three phases in under a minute with a haptic marking each transition so the sequence reads as theatre. Moodbeat maps heart rate and HRV to an emotional spectrum shown as a single colour ring, with mappings grounded in research on colour psychology and on how HR and HRV correlate with emotional state, then tested with real users for resonance.

Both work, and both illustrate the toll clearly. Biometric input cannot start immediately — it needs a baseline, which means the first thirty seconds of the product are spent not doing the thing the user opened it for. Fibber absorbs that by making calibration part of the performance. Moodbeat absorbs it by having no discrete start at all; the ring is simply always showing current state.

Neither app claims clinical accuracy, and the framing matters: Fibber is a lie detector in the sense a party game is, not in the sense a polygraph claims to be. Overstating what a biometric signal means is the most common failure in this category, and the easiest to avoid.

AR

Where the physical act is the point

Duckscape AR rebuilds light-gun hunting with ARKit and RealityKit, placing ducks in the player’s real room and turning the phone into the gun. The reasoning is specific: most remakes of light-gun games are flat touchscreen ports, and what they lose is the physical act of aiming at something in space. That act is the thing worth preserving, and AR is the only input that preserves it.

AR Filter Games on Effect House work the opposite end — fast-tap challenges, reflex timers and face-gesture games, built because most filters are static and visual and users rarely come back to a filter twice.

Duckscape AR shipped to the App Store in November 2026, and shipping it forced the clearest statement of the toll in this whole case study: Find mode needs a LiDAR scanner to hide a duck on a real surface, which a large share of devices do not have. Rather than cut the mode or raise the requirement for the whole game, it ships as two modes with different hardware floors — Shoot on any AR-capable device, Find on LiDAR. The input kept its ambition without locking anyone out. AR Filter Games remains in development.

The rule

What the pattern comes to

Sorting these by whether they removed a step or added one produces a usable rule.

Earned its place

Audio driving game difficulty, motion as measurement, voice on a watch, haptics as primary feedback. Each replaced something the user was already doing or could not do well.

Earned it with a toll

Biometric input and AR. Both need setup or environment the user has to supply, so the product has to make the setup worth sitting through rather than hiding it.

Did not earn it

The audio-context initialisation. A platform requirement surfaced to the user as a precondition they cannot see, documented in three places instead of designed away.

The test that comes out of this: if a new input needs an explanation before the first use, it is being asked to carry more than it can. Either the explanation becomes part of the experience — Fibber’s calibration, Visualizer’s start prompt — or the input is not ready.

Status

Shipped versus concept

Most of the evidence above comes from products in use; the AR work is not there yet.

Shipped

Visualizer — web

Live at visualizerwebsite.com since 2024. Game Mode shipped November 2025; Draw Mode and the recording pipeline are in the live build.

Shipped

Reflex-o, Fibber, Moodbeat — Apple Watch

All three on the App Store. Voice, haptic and biometric input all running in released products.

Shipped

Motion Lab, Roulette — Flipper Zero

Both complete. Motion Lab logs at 100 Hz to CSV; Roulette uses hardware randomness for chamber placement.

Shipped

Duckscape AR — iOS

On the App Store since November 2026. Shoot mode on any AR-capable device; Find mode requires LiDAR. Game Center leaderboards, no data collected.

In development

AR Filter Games — Effect House

A series of reflex and face-gesture filters in progress.
