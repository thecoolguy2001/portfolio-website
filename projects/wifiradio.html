October 23, 2026

Results

Version 1.0 is complete: pick an MP3 off the SD card, and up to eight people nearby can join a WiFi network and hear it live in a browser. No app on their side, no pairing, no account.

What I did not expect going in was how much of the work would be about time rather than audio. Moving bytes between two chips is easy. Moving them at exactly the rate a human ear expects to receive them, while surviving a flaky serial link, is the entire project. The audio itself is the one part neither chip ever touches.

October 23, 2026

How It Works

Three pieces, each doing the one job it is actually good at. The Flipper owns the SD card and the controls. The ESP32-S2 devboard owns the radio and the HTTP server. The listener's own phone owns the audio decoding, which is the expensive part and the part browsers have done natively for twenty years.

Flipper: the station console

Reads the MP3 from the SD card, paces the bytes out over the GPIO header, and shows listener count, link health and buffer level while it plays.

ESP32: the transmitter

Runs a WiFi access point named after your station, a DNS captive portal, and an HTTP server that fans one incoming stream out to every listener.

Phone: the receiver

Joins the network, gets handed the player page automatically by the captive portal, and decodes the stream in the browser. Playback survives switching apps.

One stream, many listeners

Everyone receives the same bytes at the same moment, so bandwidth stays flat as listeners join rather than multiplying per person.

Tune in late, like real radio

Join halfway through and you come in wherever the track has got to. It is a broadcast, not a file transfer, and it behaves like one.

Name your station

The station name is the WiFi network name, set from Settings, so people see who is broadcasting before they even join.

October 20, 2026

The Bitrate Is the Clock

The central idea is that neither chip decodes audio, and neither chip needs a timer to keep the stream in real time. The Flipper reads the bitrate out of the first MP3 frame header, converts it to bytes per second, and reads the file out at exactly that rate. Because the file's own bitrate is what playback speed means, pacing the bytes is keeping time.

This is why it only accepts constant-bitrate MPEG1 Layer III. A variable-bitrate file has no single number that describes how fast it should be consumed, so the pacing clock would drift against the audio and the stream would slowly run early or late. Constraining the input format bought the entire timing model for free, which felt like a much better trade than writing a decoder on a microcontroller to find out how fast to go.

A credit system sits underneath as a backstop: the ESP grants a byte window as its ring buffer drains, and the Flipper never sends past it. Pacing sets the speed; credit stops an overflow if anything stalls.

October 22, 2026

The Bug That Ate the Next Frame

Frames on the UART link look like [0xAA][type][len][payload][crc8]. The obvious way to recover from a corrupted frame is to scan forward for the next 0xAA start byte and resume there. On this link, that does not work, and the reason took a while to see.

0xAA is not escaped, and the payload is raw MP3 data, so the byte 0xAA occurs naturally inside the audio all the time. A scan looking for a frame boundary cannot tell a real one from a coincidence in the music. Worse, a frame cut short mid-payload does not just lose itself — the stale decoder keeps consuming, swallows the next frame's start byte as payload, and that perfectly good frame then fails CRC too. One glitch became two.

The fix was to stop trying to resync on content and resync on silence instead. If a frame is partially received and no byte arrives for 50 ms, the decoder abandons it and goes back to hunting for a start byte. At 921600 baud a full 512-byte frame takes about 5.6 ms, so 50 ms is far longer than any legitimate gap between bytes but still imperceptible in audio. The host tests cover exactly this case.

Both decoders also keep counters for frames_ok, crc_errors, oversize_errors, resyncs and truncated, surfaced on the station console. A flaky link should be something you can see and diagnose, not just something that sounds bad.

October 15, 2026

Designing the Link

With two independently built halves, the protocol between them is the real contract. It got written down as a spec first, in protocol.md, and the shared codec got host tests before either side was finished, so the two halves could be developed against the document rather than against each other.

921600 baud, with headroom

A 128 kbps stream needs 16 KB/s. The link runs at roughly three times that even at the 460800 fallback, so the audio is never competing with the ceiling.

CRC-8 on every frame

Covering type, length and payload. Cheap enough to run on both chips at full rate, and enough to catch the corruption a serial link actually produces.

Credit, not backpressure guessing

The ESP reports how many bytes it can still accept rather than the Flipper inferring it. The side that knows the buffer state is the side that reports it.

Release the UART politely

The FAP calls expansion_disable() before claiming the pins and expansion_enable() on exit, or the firmware's own expansion listener keeps ownership and nothing works.

Metadata rides the same link

Track title and artist go over as JSON on their own message type, driving the now-playing text on both the Flipper screen and the player page.

Buffer where it is cheap

A ~64 KB ring buffer on the ESP, plus the few seconds browsers buffer by themselves, smooths over UART hiccups without the Flipper needing to care.

October 12, 2026

The Listener Has to Do Almost Nothing

The hardest interaction problem here is not on the Flipper, it is on a stranger's phone. Anything that needs explaining out loud is a failure, because the person broadcasting is usually in the middle of a conversation when someone asks what they are playing.

So the flow is: join the WiFi network, and the phone opens the sign-in sheet by itself. That is standard captive-portal behaviour every phone already implements for hotel and café WiFi, and here it does the whole job of telling someone where to go. The page it lands on has one button on it.

The listener count is shown to listeners too, not just the broadcaster. Eight slots is a real limit, and the honest thing is to let people see whether there is still room rather than letting the ninth person wonder why nothing happened.

October 9, 2026

Problem

Playing music for the people around you has surprisingly bad options. A speaker fills the whole room whether everyone wants it or not. Bluetooth pairs to one device. Anything that syncs playback across phones needs every person to install the same app and usually sign in, which is far more friction than the moment is worth.

Meanwhile the Flipper's ESP32 devboard can create a WiFi network, and every phone already contains a perfectly good audio player that needs no installation at all: its browser. The pieces for a genuine local broadcast were all sitting there unconnected.

October 9, 2026

Project Started

The project began as a protocol document rather than code. Two chips, built separately, talking over one serial link, meant the thing most likely to go wrong was the boundary between them — so that boundary got specified first and tested on a host before either half existed.

Flashing the devboard does replace its stock Black Magic firmware, which is worth knowing before you start. It can be restored any time from lab.flipper.net.
